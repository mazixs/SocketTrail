1. Коротко

  • Порт реален: около 500-700 строк платформенного кода, основное в sockets, procs, capture. Веб-интерфейс, разбор pcapng, отчеты, кеш и пути уже переносимые.
  • Первый тестовый exe, который показывает соединения по процессам (без захвата трафика), получится после этапа 2. Захват и дампы появятся после этапа 3.
  • Для релизов exe собирается нативно на runner windows-2025, target x86_64-pc-windows-msvc с +crt-static. Так делают ripgrep, bat, fd, starship и Sniffnet. Для локальной разработки: x86_64-pc-windows-gnu через mingw-w64 и проверка под Wine.
  • Wine проверяет, что exe запускается, API отвечает и парсинг Windows-таблиц не падает. Соединения Linux-хоста в Wine не видны, Npcap и Edge там не работают. Полная проверка возможна только на runner windows-2025 и на вашем тестовом компьютере.
  • Npcap в сборку не кладем: лицензия запрещает редистрибуцию. Пользователь ставит Wireshark вместе с Npcap, мы вызываем его dumpcap.exe.
  • Подпись кода откладываем. Без нее SmartScreen будет предупреждать при первом запуске, это нужно честно описать в README.

Выводы из Habr

  • Кросс-компиляция через mingw работает. Грабли старых статей (winpthreads, _onexitbegin) на современном тулчейне почти не встречаются. Проверка после сборки: x86_64-w64-mingw32-objdump -p app.exe | grep DLL.
  • Exe, собранный под windows-gnu, Defender чаще удаляет по ML-эвристике, чем msvc-сборку. UPX и самораспаковка резко увеличивают число срабатываний.
  • С июня 2023 ключ подписи кода должен храниться только в токене, HSM или облаке, PFX в CI больше не подходит. Для российских юрлиц покупка сертификата рискованна (проверки по санкционным спискам, отзывы). Отечественному УЦ Windows не доверяет.
  • Схема CI из статей 2025 года: несколько build-job, результаты передаются через artifacts, отдельный job публикует релиз по тегу.
  • Про iphlpapi, Npcap из своих программ, Wine для тестов и окно браузера в режиме --app на Habr полезного почти нет. Эти данные взяты из исходников Wine, Wireshark, Sniffnet и RustNet.

5. Архитектура порта

src/
  sockets/mod.rs      Socket { proto, local, lport, remote, rport, state, pid: Option<i32> }
                      pub fn snapshot(scan_pids: &[i32]) -> Vec<Socket>
  sockets/linux.rs    /proc/net/* + inode -> pid (текущий код)
  sockets/windows.rs  GetExtendedTcpTable / GetExtendedUdpTable
  procs/mod.rs        ProcInfo, descendants() (общие)
  procs/linux.rs      /proc (текущий код, Scanner с кешем)
  procs/windows.rs    Toolhelp32 + QueryFullProcessImageNameW + NtQueryInformationProcess,
                      кеш по (pid, время старта), обрыв цепочки ppid, если родитель моложе потомка
  capture.rs          + fn dumpcap_path(), fn default_ifaces(), fn stop() по платформам
  resolve.rs          + #[cfg(windows)] ветка на hickory-resolver
  alive.rs            SSE /api/alive, счетчик клиентов, таймер выхода (обе ОС)
build.rs              winresource, только при CARGO_CFG_TARGET_OS == "windows"
.cargo/config.toml    runner wine для gnu, +crt-static для msvc
assets/sockettrail.ico

Платформенные модули подключаются через #[cfg(target_os = "linux")] и #[cfg(windows)]. Зависимости Windows объявляются в [target.'cfg(windows)'.dependencies], поэтому Linux-сборка и deb не меняются.

6. Этапы

Этап 0. Подготовка 0,5 дня

  • Закоммитить текущие правки UI.
  • .cargo/config.toml, [target.'cfg(windows)'.dependencies].
  • Закрыть Linux-код через cfg, для Windows поставить заглушки. Цель: cargo build --target x86_64-pc-windows-gnu собирается без ошибок.

Результат: exe запускается под Wine с --no-open, curl /api/state отвечает, данных нет.

Этап 1. Общий тип сокета 0,5 дня

  • Модули sockets/ и procs/, цикл опроса работает с Socket.pid вместо inode.
  • На Linux поведение не меняется. Проверка: собрать, сравнить вывод API до и после на этой машине.

Результат: рефакторинг без изменения функций, Linux-версия работает как раньше.

Этап 2. Сокеты и процессы Windows 1-1,5 дня

  • sockets/windows.rs: цикл подбора размера буфера, порты в network order (младшие 16 бит), IPv6 со scope, коды состояний TCP (1-12) в имена как в Linux-версии.
  • procs/windows.rs: снимок Toolhelp32, путь, командная строка, кеш.
  • Интеграционный тест: тест открывает TCP-соединение к себе и проверяет, что snapshot() видит его со своим PID. Под Wine этот тест работает, потому что сокет принадлежит Wine-процессу.
  • Время: tz_offset через WinAPI. Сигналы Windows.

Результат: первый тестовый exe для вашего компьютера. Показывает дерево процессов и соединения с состояниями, без захвата трафика, трафика по байтам и имен из DNS.

Этап 3. Захват через dumpcap 1 день

  • Поиск dumpcap.exe: реестр, Program Files, PATH.
  • Интерфейсы по умолчанию из dumpcap -D, фильтр NO_LOOPBACK (BPF одинаковый).
  • Живой поток через stdout и запись дампа. Остановка через CTRL_BREAK, запасной вариант TerminateProcess.
  • Диагностика в UI: Wireshark не найден, Npcap только для администраторов, нет интерфейсов. Тексты с инструкциями для Windows.

Результат: трафик по байтам, SNI и DNS-имена из пакетов, дампы pcapng. Проверяется только на реальной Windows.

Этап 4. Имена и окно 1 день

  • resolve.rs: PTR и TXT (Team Cymru) через hickory-resolver с таймаутом.
  • alive.rs: SSE-heartbeat, выход при закрытии окна на обеих ОС. В UI EventSource и sendBeacon.
  • Edge: профиль в %LOCALAPPDATA%\SocketTrail\ui-profile, флаг --disable-background-mode.
  • Второй запуск: если порт занят нашим сервером, просто открыть окно и выйти.

Результат: функциональный паритет с Linux, кроме Proton.

Этап 5. Оформление exe 0,5 дня

  • assets/sockettrail.ico из svg (16-256 px), build.rs с winresource, манифест.
  • Скрипт сборки zip, раздел Windows в README: Wireshark + Npcap, предупреждение SmartScreen, права.

Результат: exe с иконкой и сведениями о версии, zip для раздачи.

Этап 6. CI/CD 0,5-1 день

  • .github/workflows/ci.yml и release.yml (см. ниже).
  • Первый релиз по тегу: deb, zip, SHA256SUMS, attestations.

Результат: релиз собирается по git tag v0.2.0 && git push --tags.

Потом, по необходимости

  • Подпись кода: SignPath Foundation (бесплатно для OSS с MIT, издателем в подписи будет SignPath Foundation) или Azure Artifact Signing. Для вашего случая доступность нужно проверить отдельно.
  • GUI-подсистема без консоли плюс значок в трее.
  • winget (winget-releaser), Scoop, MSI через cargo-wix.
  • ETW для короткоживущих процессов (как в RustNet), ARM64.

Итого около 5-6 рабочих дней чистой работы. Узкое место - циклы проверки на реальной Windows: этапы 2, 3 и 4 требуют вашего запуска на тестовом компьютере.

Чек-лист для тестового компьютера

  1. Скачать zip, распаковать, запустить sockettrail.exe. Зафиксировать, что показал SmartScreen и Defender.
  2. Открылось окно Edge с интерфейсом, иконка на панели задач.
  3. Дерево процессов: браузер, мессенджеры, svchost. Выбор процесса фильтрует соединения.
  4. Без Wireshark: понятное сообщение, как включить захват.
  5. С Wireshark и Npcap: трафик по байтам, SNI, запись дампа, файл открывается в Wireshark.
  6. Закрыть окно: процесс sockettrail.exe завершается за 10-15 с, начатый дамп закрыт корректно.
  7. При проблемах прислать вывод консольного окна.

9. Риски и ограничения

  • Антивирусы и SmartScreen. Неподписанный exe будет получать предупреждение. Меры: msvc-сборка, VERSIONINFO, без UPX, при ложном срабатывании отправка в Microsoft (wdsi/filesubmission).
  • Права. Без администратора у системных процессов нет пути и командной строки, только имя. Для большинства задач этого хватает.
  • Переиспользование PID. Строка таблицы может пережить процесс. Защита: сверка времени старта процесса.
  • Короткоживущие процессы. Опрос раз в секунду пропускает соединения, прожившие меньше секунды. Их трафик виден в пакетах как "только пакеты", как и на Linux. ETW решает это, но потом.
  • Proton/Wine-признак на Windows не имеет смысла и скрывается в UI.
  • Wine не заменяет Windows. Таблицы сокетов в Wine 10 строятся wineserver только для Wine-процессов (так с сентября 2024), Npcap-драйвер и Edge не работают.
  • Npcap ограничен лицензией: бесплатный до 5 систем, встраивать в дистрибутив нельзя. Мы только требуем установленный Wireshark.
