# Как это работает

[English](../how-it-works.md) | **Русский** · [К README](../../README.ru.md)

## Почему не хватало существующих инструментов

- `ss -tunp` в цикле пропускает соединения короче интервала опроса, а они часто самые
  интересные: отправка отчетов о падении, телеметрия, API-запросы при старте.
- `nethogs` и `iftop` показывают объем трафика, но не адреса и не домены.
- Wireshark видит пакеты, но не знает, какому процессу они принадлежат.
- Под Proton процесс не один: Steam, `pressure-vessel`, `wineserver` и сам `.exe`, а
  сокеты принадлежат дочерним процессам. Если выбрать один PID, половина картины
  теряется.

SocketTrail объединяет два источника. Быстрый опрос таблиц сокетов дает владельца
каждого соединения. Разбор потока пакетов дает домены и соединения, которые опрос не
поймал.

```
dumpcap -w - ── pcapng ──> свой парсер ──> DNS, SNI, байты ──┐
                                                             ├──> история ──> UI
таблицы сокетов ── 250 мс ──> сокеты ──> PID владельца ──────┘       │
                                                              PTR, ASN, кеш
```

Пакет сопоставляется с процессом по кортежу: протокол, локальный адрес и порт,
удаленный адрес и порт. Соединение, закрывшееся между двумя опросами, остается в
истории строкой только из пакетов, без выдуманного владельца.

## Сокеты и процессы

**Linux.** Сокеты читаются из `/proc/net/{tcp,tcp6,udp,udp6}`, без запуска `ss`.
Владелец находится через inode сокета в `/proc/<pid>/fd`. Обходить дескрипторы всех
процессов дорого, поэтому выбранная группа сканируется на каждом опросе, а полная
карта компьютера — примерно раз в 2 секунды.

Wine держит копию каждого сокета Windows-программы в `wineserver`. Такой сокет
приписывается самому `.exe`, иначе соединения игры уходили бы к `wineserver`.

Процесс получает плашку PROTON, если в его командной строке есть Proton, Wine или
pressure-vessel либо его имя начинается с `wine` или заканчивается на `.exe`. Такой
процесс показывается по имени `.exe` из командной строки: имя Wine-процесса в ядре
обрезано до 15 символов и часто оказывается просто именем потока вроде `GameThread`.

Вместе с процессом выбирается все его поддерево, а группа пересчитывается на каждом
полном проходе, потому что Proton запускает новых потомков прямо во время игры.

**Windows.** Сокеты берутся из `GetExtendedTcpTable` и `GetExtendedUdpTable` вместе с
PID владельца, процессы — из Toolhelp32.

Владелец UDP определяется по локальному адресу, порту и семейству IP, а у
подключенного сокета — еще и по удаленному адресу и порту. Привязки к `0.0.0.0`
и `::` сопоставляются только с адресами этого компьютера, прочитанными из сетевых
интерфейсов. При общем порте или неизвестном владельце процесс не выбирается
произвольно. На Linux повторное использование сокета определяется по inode, на
Windows — по времени создания UDP-сокета. Если Windows не отдает время создания,
используется таблица с PID.

Новый сокет не получает пакеты, накопленные до его наблюдаемого времени жизни.
Если один кортеж содержит пакеты разных сокетов, запись остается без владельца,
а вся история не переподписывается последним процессом. Опрос таблиц по-прежнему
не позволяет надежно определить сокет, созданный и закрытый между опросами.

Для TCP смена inode или PID делает объединенную историю спорной, как и повторное
открытие закрытого кортежа, если его снова не держит тот же экземпляр процесса.
Счетчики сохраняются, но PID, имя процесса и прежний SNI сбрасываются. Такой кортеж
исключается из выборки процесса и его дампа.

На Windows поле состояния в таблице TCP бывает смещено относительно строк: у
установленных соединений встречаются значения вроде LISTEN или 0. Таблица с невозможными
строками считается смещенной: состояния, которые дает смещение, не меняют состояние
соединения, а строка без владельца считается TIME_WAIT. Поэтому мигающая строка не
закрывает соединение и не делает его владельца спорным.

Идентичность процесса включает время запуска, а не только PID. Повторный PID
не попадает в прежнюю группу записи и не сохраняет старый выбор. Выбранные и
записываемые процессы проверяются при каждом опросе. Если несколько Linux-процессов
держат один inode, владелец остается неоднозначным, в том числе после частичного
обхода; копия Wine в `wineserver` остается отдельным случаем.

## Пакеты

На Linux `dumpcap` из Wireshark пишет поток pcapng в stdout, и SocketTrail разбирает
его своим парсером, без libpcap. Для `dumpcap` нужны capabilities на захват, а не root.
Трафик loopback не захватывается, кроме DNS: при большом локальном трафике он только
зря нагружал бы разбор.

На Windows от администратора запускается встроенный драйвер PktMon штатной утилитой
`pktmon`, а кадры читаются из отдельной ETW-сессии. Без прав администратора домены
берутся из DNS-кеша системы (`DnsGetCacheDataTable`). См. [Windows](windows.md).

Из пакетов SocketTrail берет:

- DNS-ответы: имена, адреса и цепочки CNAME;
- SNI из TLS ClientHello;
- SNI из пакетов QUIC Initial (HTTP/3);
- байты и пакеты по каждому соединению;
- соединения, которых таблица сокетов так и не показала.

QUIC шифрует даже первые пакеты, но ключи Initial выводятся из идентификатора
соединения, который идет открытым текстом (RFC 9001), поэтому ClientHello читается без
ключей сессии. Поддерживаются версии 1 и 2. Chrome раскладывает ClientHello на
несколько пакетов и перемешивает кадры, поэтому куски собираются по смещению для
каждого соединения. С Encrypted Client Hello (ECH), в TLS и в QUIC одинаково, виден
только внешний SNI: публичное имя провайдера, например `cloudflare-ech.com`.

TLS ClientHello собирается из нескольких TCP-сегментов и TLS-записей, с учетом
перестановки сегментов, повторных передач и перехода счетчика sequence number.
Для каждого направления хранятся до 32 КиБ потока и 16 КиБ рукопожатия; одновременно
до 256 потоков, с удалением после 10 секунд простоя. QUIC восстанавливает сокращенные
номера пакетов перед расшифровкой. Разбираются Ethernet VLAN/QinQ и заголовки IPv6
hop-by-hop, routing, destination, AH и первого фрагмента. IP-фрагменты не собираются.

Живой захват сохраняет кадры целиком. Очередь учета ограничена 65 536 разобранными
пакетами, а соединения попадают в сведения записи раз за опрос, а не под блокировкой на
каждый пакет. На Windows ETW-callback только копирует событие в очередь с пределом
256 МиБ; рабочий поток разбирает и пишет кадры, а управление записью идет через ту же
очередь. Типы кадров, которые PktMon сообщает, а SocketTrail не разбирает, считаются
отдельно и потерями не являются. Запуск PktMon останавливает только захват, оставшийся
от прошлого запуска SocketTrail; чужой захват не затрагивается, а занятый захват дает
ошибку запуска. Потери при перегрузке видны в статистике API и подсказке индикатора
захвата.

Непервые IPv4-фрагменты не разбираются как TCP/UDP: в них нет транспортного
заголовка. Пересборки IP-фрагментов нет, поэтому счетчики фрагментированного
трафика могут быть неполными. Полный дамп сохраняет все кадры; дамп процесса
исключает фрагменты, для которых нельзя подтвердить владельца.

## Имена и владельцы сетей

Имена берутся из SNI, DNS-ответов, PTR и подписей для особых адресов, в таком порядке
надежности. Адрес за цепочкой CNAME получает запрошенное имя, а не узел CDN в конце
цепочки. PTR запрашивается через `resolvectl`, запасной путь — `dig`, на Windows —
через `DnsQuery_W`. Найденные имена сохраняются в `names.json` в каталоге кеша:
DNS-ответ виден только один раз, и без кеша соединение, открытое до запуска
SocketTrail, после перезапуска осталось бы без имени.

DNS-имена истекают по TTL записи, но не позднее суток. Для IP хранятся до восьми
имен; несколько действующих имен или переполнение означают неоднозначное DNS-имя
нового соединения. Уже известное соединение сохраняет первое DNS-имя, пока его не
заменит SNI. Дисковый кеш сохраняет срок действия и неоднозначность; старые DNS-записи
без TTL не восстанавливаются. DNS по-прежнему дает предположение для IP, а не
доказательство имени конкретного соединения или процесса.

Владелец сети — это ASN от [Team Cymru](https://www.team-cymru.com/ip-asn-mapping),
запрошенный как TXT-запись DNS у `origin.asn.cymru.com`. PTR и ASN часто расходятся,
например PTR хостинговой компании в сети Cloudflare, поэтому хранится и то и другое.
Адреса опознаются в фоне по несколько штук за раз, с кешем. Запрашиваются только
публичные адреса: для частных, link-local, CGNAT (`100.64.0.0/10`, в том числе
Tailscale) и зарезервированных запрос раскрыл бы внешнему резолверу адреса вашей
сети. Делегированная обратная зона (RFC 2317) не считается именем PTR, а если Team
Cymru называет несколько исходных ASN, показывается первый.

## Дампы

Дамп — это второй `dumpcap` (или поток PktMon на Windows), который пишет пакеты
целиком в файл. При остановке SocketTrail один раз переписывает файл:

1. С галочкой **только процесс** остаются пакеты соединений, которыми владеет
   выбранная группа. Подтвержденные привязки сохраняются на время записи даже
   после вытеснения старых соединений из текущей истории. Соединения, открытые
   после старта, тоже попадают в файл. Неизвестные и спорные владельцы исключаются:
   общий IP или домен CDN не доказывает принадлежность одному процессу.
2. С настройкой **Сокращать файл** пакеты за пределами первых 64 КиБ потока сохраняют
   заголовки и 16 байт данных, кадры, которые не удалось разобрать, — 128 байт, а DNS
   остается целиком. Уменьшается только записанная длина: исходная остается в блоке
   пакета, поэтому Wireshark показывает настоящие размеры.
3. Каждый пакет получает комментарий pcapng `процесс [pid] -> домен`, а в заголовке
   секции написано, что именно записано.
4. С настройкой **Разбивать на части** переписанный файл копируется в `<дамп>.parts/`,
   по файлу на домен или подсеть, и свой файл получают 64 самые объемные группы.
5. `<дамп>.json` хранит сводку с `format: 2`, а `<дамп>.connections.jsonl` — по строке на
   соединение с тем, что посчитано по файлу. Потоки из файла, которых нет в карте, тоже
   перечислены и отмечены как чужие.

Те же шаги запускаются повторно из панели **Дампы**. Сокращение и разбиение сохраняют
состав файла, меняет его только явный отбор. Обработка идемпотентна: подписи заменяются,
а вырезанные данные сокращенного файла не возвращаются. Сводка прежнего
формата с массивом `conns` тоже читается и переводится в новый, а локальные адреса ее
соединений помогают определить направление потоков, которых нет в карте.

Запись "только процесс" останавливается сама через 15 секунд после выхода процесса.

Запуск, запись и завершение — отдельные состояния. Повторный старт и другие
операции во время запуска или завершения отклоняются без изменения записи.
На Linux начало захвата подтверждается потоком pcapng или заголовком файла;
завершение dumpcap отслеживается вместе с его диагностикой. На Windows проверяются
состояние ETW и ошибки записи файла. Имена файлов уникальны даже при быстрых запусках.

При ошибке остановки, обработки или сохранения карты API возвращает `ok: false`,
а интерфейс показывает ошибку. Если отбор процесса не выполнен, исходный захват
сохраняется и явно помечается как нефильтрованный. В JSON `requested_only_process`
описывает запрос, `only_process` — результат; `processing` содержит статус обработки
и признак корректного завершения захвата `capture_complete`.

Метаданные записи ограничены 100 000 кортежами соединений и 4096 экземплярами
процессов. Достижение лимита не останавливает запись: соединения сверх него остаются без
подписи и не проходят отбор процесса, а в сводку добавляется предупреждение. При
завершении программа до двух секунд ждет учета уже принятых пакетов.

Отбор выполняется всегда. Неизвестное соединение и так исключается, поэтому потери при
захвате могут сделать файл только неполным, но не перемешают в него чужой трафик. Они
становятся предупреждениями и `capture_complete: false`. Обрезанные блоки и несовпадающие
длины pcapng оставляют исходный файл нетронутым, как и отбор, после которого не осталось
бы ни одного пакета.

История пока консервативно объединяет повторные жизни одного кортежа, а время
отражает наблюдение, а не захват на сетевом интерфейсе. Разделение этих жизней и
сопоставление по времени захвата остаются следующей доработкой движка. Когда оба
конца соединения находятся на этом компьютере, пакеты учитываются как исходящие
у отправителя; счетчики приема второго локального сокета не дублируются.

## Локальный интерфейс

Интерфейс — это один HTML-файл, вшитый в бинарь и отдаваемый встроенным HTTP-сервером
на `127.0.0.1`. Запросы с `Host`, отличным от `127.0.0.1:<порт>` и `localhost:<порт>`,
отклоняются, это закрывает DNS rebinding. POST-запросы с чужим `Origin` отклоняются,
это закрывает CSRF со страниц, открытых в браузере.

Окно держит открытым SSE-канал `/api/alive`. Когда окно закрыто и канал молчит 10
секунд, программа дописывает дамп и завершается. На Linux она еще следит за процессом
браузера своего профиля по ссылке `SingletonLock` в профиле и выходит сразу после его
завершения. Если процесс найти не удалось, остается только канал.

Таблица считается на сервере. `/api/state` принимает выборку, вид, порядок, отбор и
страницу и сериализует только строки страницы, вне блокировки истории. `/api/facets` и
`/api/export` принимают те же параметры, поэтому списки значений и отчеты всегда
совпадают с таблицей. Время появления соединения — порядок по умолчанию и второй ключ
сортировки, потому что оно не меняется, пока соединение живо; списки значений
упорядочены независимо от счетчиков по той же причине.

## Устройство кода

| Модуль | Назначение |
|---|---|
| `src/main.rs` | запуск, командная строка, окно, завершение |
| `src/app.rs` | состояние приложения, циклы разбора пакетов и опроса, фоновое опознание адресов |
| `src/api.rs` | HTTP API и проверка запросов |
| `src/query.rs` | отбор, сортировка, страницы, сводки и списки значений таблицы |
| `src/recording.rs` | жизненный цикл записи: старт, учет владельцев, остановка, повторная обработка |
| `src/dumpfile.rs` | файлы дампа: обработка, сводка, карта соединений, части, прежний формат |
| `src/localtime.rs` | местное время для имен файлов и подписей, без зависимостей |
| `src/procs/` | список процессов: `/proc` на Linux с определением Proton, Toolhelp32 на Windows; дерево потомков |
| `src/sockets/` | снимок сокетов: `/proc/net/*` и inode -> PID на Linux, таблицы IP Helper на Windows |
| `src/pcap.rs` | разбор потока pcapng, SNI из TLS ClientHello, DNS-ответы |
| `src/tls.rs` | ограниченная сборка TLS ClientHello из TCP-потока |
| `src/quic.rs` | SNI из QUIC Initial: ключи, расшифровка, сборка ClientHello |
| `src/capture/` | платформенный захват: dumpcap на Linux, свой движок PktMon/ETW на Windows |
| `src/etw.rs` | Windows: захват через PktMon и ETW, запись `.pcapng` |
| `src/dnscache.rs` | Windows: имена из DNS-кеша системы |
| `src/annotate.rs` | перезапись pcapng: подписи пакетов, отбор трафика процесса, сокращение, разбиение |
| `src/resolve.rs` | запросы PTR и ASN |
| `src/cache.rs` | кеш имен на диске |
| `src/state.rs` | история соединений, счетчики, слияние имен |
| `src/report.rs` | автономный HTML-отчет |
| `src/i18n.rs` | тексты на английском и русском, выбор языка |
| `src/window.rs` | окно в браузере на Chromium со своим профилем, открытие папок |
| `src/alive.rs` | SSE-канал, по которому видно, что окно закрыто |
| `src/elevate.rs` | Windows: проверка прав и перезапуск от администратора |
| `src/win_startup.rs` | Windows: оконный запуск и журнал в файле |
| `src/paths.rs` | каталоги кеша и дампов |
| `ui/index.html` | весь интерфейс, вшит в бинарь |
