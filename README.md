# SocketTrail

Монитор сетевых соединений с привязкой к процессу - в том числе к приложениям
под Proton и Wine. Показывает домен, IP, порт, протокол, владельца сети и объем
трафика по каждому соединению, ведет историю (закрытые соединения не исчезают)
и по одной кнопке пишет весь трафик выбранного процесса в единый файл .pcapng.

```
 SocketTrail        [ Живые ] [ С трафиком ] [ Все ]     [Дампы] [Отчет HTML]
┌────────────────────────┬──────────────────────────────────────────────────┐
│ ● steam        PROTON  │ Время   Состояние   Домен            Порт  Сеть  │
│   └ srt-bwrap          │ 21:04   ESTABLISHED api.example.com   443  AS13335│
│     └ pv-adverb        │ 21:04   только пакеты cdn.example.net 443  AS16509│
│       └ game.exe   ●   │ 21:03   TIME_WAIT   192.0.2.10        27015 AS64500│
│ ● chrome  x12          │ 21:03   ESTABLISHED (UDP) 192.0.2.44   443  AS15169│
│   firefox              │ ...                                              │
├────────────────────────┴──────────────────────────────────────────────────┤
│ [x] Собрать дамп   [ ] только адреса процесса   [ ] Сводка по адресам     │
└───────────────────────────────────────────────────────────────────────────┘
```

Слева - дерево процессов с автообновлением, справа - история соединений с
доменом, адресом, портом, владельцем сети и объемом трафика. Режим "Сводка по
адресам" сворачивает историю в одну строку на цель с числом сессий.

## Почему не хватало готовых утилит

- `ss -tunp` в цикле не видит соединения короче интервала опроса, а именно такие
  чаще всего и интересны (отправка отчета об ошибке, обращение к API при старте).
- `nethogs` и `iftop` показывают объем, но не адреса и не домены.
- Wireshark видит пакеты, но не знает, какому процессу они принадлежат.
- Под Proton процесс не один: Steam, `pressure-vessel`, `wineserver` и сам `.exe`,
  причем сокеты висят на дочерних процессах. Выбор одного PID теряет половину картины.

SocketTrail совмещает оба источника: быстрый опрос таблиц сокетов дает владельца,
разбор пакетного потока дает домены (DNS и SNI) и те соединения, которые опрос
не успел застать.

## Требования

Linux, `dumpcap` из состава Wireshark. Root не нужен, если выполнено штатное
условие Wireshark - у `dumpcap` есть capabilities, а пользователь состоит в группе
`wireshark`:

```sh
sudo dpkg-reconfigure wireshark-common   # ответить "да"
sudo usermod -aG wireshark "$USER"       # затем перелогиниться
getcap /usr/bin/dumpcap                  # cap_net_admin,cap_net_raw=eip
```

Без `dumpcap` утилита продолжает работать, но остается только опрос сокетов:
доменов и коротких соединений не будет, о чем сообщает индикатор в заголовке.

## Установка

```sh
./install.sh
```

Кладет бинарь в `~/.local/bin`, ярлык в меню приложений и проверяет окружение -
есть ли `dumpcap`, выданы ли ему права, виден ли `~/.local/bin` в `PATH`.
Права root не нужны. Откат - `./uninstall.sh`.

## Запуск

| Способ | Команда |
|---|---|
| Из меню приложений | значок **SocketTrail** (раздел Сеть) |
| Из терминала после установки | `sockettrail` |
| Из репозитория, без установки | `./run.sh` - соберет, если исходники новее бинаря |
| Через make | `make run`, `make install`, `make check` |
| Вручную | `cargo build --release && ./target/release/sockettrail` |

Откроется окно (Chrome в режиме `--app`, иначе вкладка браузера). Сервер слушает
только `127.0.0.1`. Повторный запуск не плодит копии: если SocketTrail уже
работает, открывается его окно; если порт занят чужой программой, берется следующий.

Ключи: `-i <интерфейс>` (по умолчанию `any`), `--port <порт>` (по умолчанию 8787),
`--no-open` - только сервер, без окна, `--help` - справка.

### Фоновый сбор, по желанию

Чтобы история копилась еще до открытия окна - например, с момента входа в систему,
до запуска игры:

```sh
mkdir -p ~/.config/systemd/user
cp assets/sockettrail.service ~/.config/systemd/user/
systemctl --user enable --now sockettrail
```

Учтите: в этом режиме `dumpcap` работает постоянно и разбирает весь трафик хоста.

## Как пользоваться

1. Слева выбрать процесс. Список обновляется сам, зеленая точка - есть активные
   соединения, бейдж PROTON - процесс исполняется под Proton или Wine.
   Выбор процесса автоматически включает все его дочерние процессы.
2. В таблице появится история соединений. Строки с бейджем "только пакеты" -
   соединения, пойманные пакетным разбором, но не заставшие таблицу сокетов.
3. "Собрать дамп" пишет `~/SocketTrail/<процесс>-<дата>.pcapng` - это папка
   SocketTrail в домашнем каталоге, а не каталог репозитория, у которого такое
   же имя. Кнопка "Дампы" в шапке показывает полный путь, список уже собранных
   файлов и открывает папку в файловом менеджере. Галочка
   "только адреса процесса" ставит BPF-фильтр по уже известным адресам, иначе
   в файл попадет весь трафик хоста. Рядом сохраняется `.json` с картой
   соединений, доменов и PID - чтобы через неделю было понятно, что снималось.
4. "Отчет HTML" выгружает автономный файл, который открывается без интернета.

### Мелочи, которые экономят время

- Дерево процессов раскрывается: у родителя видно всех потомков, а десяток
  одноименных листьев (вкладки браузера, воркеры) сворачивается в строку
  вида `chrome x12`.
- Границы колонок перетаскиваются, двойной клик по границе подгоняет колонку
  под самое длинное значение - длинные домены читаются целиком. Ширины
  запоминаются, как и ширина левой панели.
- Кнопка с иконкой копирования в строке кладет в буфер домен или адрес,
  "Копировать" в шапке - всю показанную таблицу как TSV, готовый для таблиц.
- "Сводка по адресам" сворачивает историю по паре адрес-порт: вместо трехсот
  строк TIME_WAIT к одному узлу видно одну строку с числом сессий и трафиком.
- Флажки "локальные адреса" и "соединения SocketTrail" показывают то, что по
  умолчанию скрыто: обращения к 127.0.0.53, mDNS, SSDP и собственный служебный
  трафик программы.

### Про порты и имена

Порт всегда настоящий. Для живых соединений он читается из
`/proc/net/{tcp,tcp6,udp,udp6}`, для пойманных пакетным разбором - из
заголовка TCP или UDP. Значений по умолчанию, догадок по типу службы и любых
других подстановок в коде нет: если порт неизвестен, строки не будет вовсе.

Имя узла берется из четырех источников по убыванию надежности: SNI из TLS
ClientHello, ответы DNS, PTR-запись, затем подпись для служебных адресов
(`127.0.0.53` - это сам системный резолвер, домена у него не бывает).
Найденные имена складываются в `~/.cache/sockettrail/names.json` и переживают
перезапуск: DNS-ответ пролетает один раз, и без кеша соединение, открытое до
запуска SocketTrail, осталось бы безымянным.

## Устройство

| Модуль | Назначение |
|---|---|
| `src/procs.rs` | инвентаризация процессов через /proc, распознавание Proton и дерева потомков |
| `src/sockets.rs` | парсер /proc/net/{tcp,tcp6,udp,udp6} и привязка inode сокета к PID |
| `src/pcap.rs` | разбор потока pcapng, извлечение SNI из TLS ClientHello и адресов из DNS-ответов |
| `src/capture.rs` | управление dumpcap: живой поток и запись дампа |
| `src/resolve.rs` | PTR и ASN через resolvectl (запасной путь - dig) и Team Cymru; показываются оба, потому что они часто расходятся |
| `src/cache.rs` | кеш найденных имен на диске, чтобы они не терялись между запусками |
| `src/state.rs` | история соединений, счетчики, сведение имен |
| `src/report.rs` | автономный HTML-отчет |
| `ui/index.html` | интерфейс, вшит в бинарь |

## Windows

Запланировано отдельной фазой. Заменяются два модуля: `sockets.rs` на
`GetExtendedTcpTable`/`GetExtendedUdpTable` и `capture.rs` на Npcap. Ядро
состояния, разбор пакетов и интерфейс переносятся без изменений.
