# SocketTrail - план реализации

## 1. Выбранный стек и почему

| Слой | Решение | Обоснование |
|---|---|---|
| Ядро | **Rust** (stable 1.96) | Один статический бинарь без рантайма, ~5 МБ, опрос сокетов каждые 200 мс без нагрузки. Уже установлен. |
| Сбор соединений | Собственный парсер `/proc/net/{tcp,tcp6,udp,udp6}` + `/proc/<pid>/fd` -> inode | Быстрее и точнее, чем `ss` в цикле (нет форка процесса на каждый опрос). Практика из отчета: сокеты живут на `GameThread` и дублируются на `wineserver`, поэтому нужен обход всего дерева задач, а не одного PID. |
| Пакетный захват | `dumpcap -i any -w -` , поток pcapng в stdin + **собственный парсер pcapng** | `dumpcap` уже имеет `cap_net_admin,cap_net_raw`, пользователь в группе `wireshark` -> **root не нужен**. Свой парсер снимает зависимость от libpcap-dev (не установлен) и дает полный контроль. |
| Обогащение | Свой разбор DNS-ответов (A/AAAA/CNAME) и TLS ClientHello (SNI) прямо в потоке пакетов | Закрывает главное слепое пятно: у боевого сервера нет PTR и DNS-имени, имя шарда дал только SNI. Короткие соединения (nccr-api) опросом сокетов не ловятся в принципе. |
| Опознание владельца | PTR + ASN через `origin.asn.cymru.com` + RDAP, асинхронно, с кешем | Практика из отчета: RDAP и ASN расходятся (Global QTcom по RDAP против AS13335 Cloudflare по факту). Показываем оба. |
| GUI | Встроенный HTTP + WebSocket сервер, UI = один HTML-файл, вшитый в бинарь | Легковесно, красиво, кроссплатформенно без изменений. Запуск окна через `chrome --app` / `xdg-open`. Нативную обертку (Tauri) можно добавить позже - webkit2gtk в системе отсутствует, ставить его ради рамки окна нерационально. |

**Отвергнуто на первом этапе:** eBPF (нет clang и libbpf, требует root с паролем); Electron/Tauri (вес и зависимости); Python (медленный опрос, тяжелая раздача). eBPF заложен как опциональный бекенд фазы 3 для гарантии по сверхкоротким соединениям.

## 2. Архитектура

```
dumpcap -i any -w -  ──pcapng──▶ parser ──▶ DNS / SNI / байты  ┐
                                                                ├─▶ Ядро состояния ─ws─▶ UI
/proc/net/* + /proc/*/fd ──200 мс──▶ сокеты ──▶ привязка к PID  ┘         │
                                                                    PTR / ASN / RDAP
```

Корреляция: пакет привязывается к процессу по кортежу (локальный порт, удаленный адрес, порт), который держит таблица сокетов. Для соединений, закрывшихся между опросами, остается запись из пакетного потока со статусом "процесс не определен точно" - честнее, чем потерять их.

## 3. Этапы

1. **Каркас.** Cargo-проект в корне репозитория, HTTP+WS сервер, вшитый UI, список процессов с автообновлением.
2. **Сокеты.** Парсер /proc/net, привязка inode->PID, дерево процессов (Proton: steam -> pressure-vessel -> wineserver -> *.exe), группировка соединений по выбранному процессу, история (соединение не исчезает из списка после закрытия).
3. **Пакетный слой.** Запуск dumpcap, разбор pcapng, DNS и SNI, счетчики байт и пакетов на соединение.
4. **Дамп.** Кнопка "Собрать дамп": второй поток dumpcap пишет в единый .pcapng в выбранную папку, рядом кладется .json с картой процесса, адресов и доменов.
5. **Обогащение.** PTR, ASN, RDAP с кешем на диске.
6. **Экспорт отчета** в автономный HTML в стиле уже накопленного отчета.
7. **Windows (отдельная фаза).** Замена двух модулей: сокеты -> `GetExtendedTcpTable`/`GetExtendedUdpTable`, захват -> Npcap. UI и ядро состояния остаются без изменений.
